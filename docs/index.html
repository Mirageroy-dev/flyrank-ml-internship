0. Abstract

This project asks which content pages should be prioritized for human review based on observable content and search performance signals.

The analysis uses the FlyRank ML Internship dataset and public-safe derived features describing page visibility, freshness, engagement, and performance trends.

A transparent baseline scoring approach was first created, followed by machine learning analysis and validation designed to evaluate whether the resulting ranking improves content prioritization.

The final evaluation compares the model and baseline on the same validation design and reports the measured ranking performance of each approach.

The output is a ranked decision-support queue with reason codes that helps an editor decide which pages deserve review first.

1. Problem Framing

Decision supported: The project supports decisions about which pages should be reviewed first for refresh, improvement, protection, monitoring, or other editorial action.

Unit of analysis: Each row represents one content page described by its available observable performance and content signals.

Output: A ranked action queue containing a score, priority level, and reason codes.

Human action: An editor reviews the highest-priority pages first and decides whether refresh, improvement, monitoring, or no immediate action is appropriate.

Cost of a wrong call: A false positive can waste editorial time on a page that did not need attention. A false negative can cause an important opportunity or declining page to be reviewed too late.

Data and machine learning are useful because the number of pages can exceed the number that a human team can manually inspect. A ranked system helps focus limited review capacity on pages with stronger evidence of potential need.

2. Data Safety

This project uses public-safe, pseudonymized content and performance data provided for the FlyRank ML Internship.

Data used

  • Content and page-level identifiers where permitted.
  • Historical impressions and visibility signals.
  • Clicks and click-through rate context.
  • Position and ranking context.
  • Freshness and content age information.
  • Engagement and session-related signals where available.

Deliberately excluded fields

  • trend_direction was not used as a normal predictive feature when it could directly encode the target or decision being evaluated.
  • trend_pct was excluded where it represented label-derived or future-window information.
  • Pseudonymous IDs were used only for grouping or data management and were never treated as predictive features.
  • Client-identifying information was excluded from the public report.
  • Domains, private URLs, raw search queries, credentials, and other identifying details do not appear in the public output.
Data safety confirmation: The public-facing project is intended to contain no client-identifying information in the published report or public-safe outputs.

3. Baseline

The first approach was a transparent rule-based baseline. The baseline prioritizes pages using observable warning signals such as staleness, visibility, and performance decline.

A simple baseline is important because it provides a clear comparison point. A more complex model is only useful if it improves on a rule that a human can already understand.

Baseline scoring logic

  • Stale pages receive additional priority.
  • Pages with meaningful visibility receive additional priority because an issue may affect more users.
  • Pages showing decline-related warning signals receive additional priority.

The baseline score is used to create a ranked queue and reason codes explaining why each page received its priority.

Measured baseline results: The exact baseline metric values should match the results generated by the committed evaluation notebook or metrics file. Do not replace this section with invented values.

4. Model / Analysis

The project uses the Refresh / Content Opportunity Scoring lane. The goal is to determine whether multiple observable signals can improve the prioritization of pages for human editorial review.

Method

The analysis builds features from available historical content and search performance information and evaluates whether a machine learning model or structured analysis improves ranking performance compared with the transparent baseline.

Feature categories

  • Historical visibility and impressions.
  • Click and click-through-rate context.
  • Average search position.
  • Content age and freshness.
  • Engagement or session context where available.
  • Content metadata and safe categorical context.

Features intentionally left out

  • Label-derived fields.
  • Future-window performance metrics.
  • Pseudonymous identifiers as predictive features.
  • Unsafe client-identifying information.

Target or proxy

The exact target or proxy definition is defined in the project's modeling notebook and must use information that is valid at the prediction point.

5. Evaluation

The validation design is selected to match the decision problem and reduce the risk of overly optimistic results.

Where future movement is being evaluated, a time-aware design is preferred so that earlier observations are used for training and later observations are reserved for evaluation.

Metrics

Ranked action systems should be evaluated using metrics that reflect how the output will actually be used. These can include:

  • Precision at K.
  • Recall.
  • Average precision.
  • ROC-AUC where appropriate.
  • Lift over the transparent baseline.

Base rate

The majority-class percentage or task base rate must be reported next to metrics such as accuracy or Precision@K. This prevents a high score from being presented without the context needed to judge whether the result exceeds a simple majority-class strategy.

Model vs baseline

The model and baseline must be evaluated on the same split and with the same relevant metric.

Error analysis

The evaluation includes inspection of incorrect or weak recommendations. False positives may represent pages that receive high priority despite limited practical need, while false negatives may represent pages that were not prioritized despite requiring attention.

6. Interpretation

The purpose of interpretation is to explain which observable patterns are associated with higher priority scores or model predictions.

Feature importance or other model interpretation methods are translated into plain language rather than presented as proof of causal ranking factors.

Interpretation rule: Observed relationships are reported as associations or directional findings. The project does not claim that the model discovered or predicted Google's algorithm.

Surprising findings and negative results are also important. A signal that does not improve prioritization is documented rather than being presented as useful without evidence.

7. Recommendation

The final output supports a ranked editorial workflow. A FlyRank editor can begin with the highest-priority pages, inspect the associated reason codes, and decide whether a refresh or another action is justified.

Priority Suggested Human Action
High Review first and inspect the reason codes before deciding on an editorial action.
Medium Monitor or review when editorial capacity allows.
Low No immediate action based on current evidence.

Confidence: Recommendations are decision-support signals rather than guarantees of future performance.

Limit: A high-priority recommendation does not prove that refreshing a page will improve its performance. Human review and, where necessary, experimentation are required to establish causal effects.

  5. Re-run the final evaluation and compare the generated metrics with this report.
